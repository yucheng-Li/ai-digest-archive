### Anthropic Engineering

**《How we contain Claude across products》**（作者：Max McGuinness、Mikaela Grace、Jiri De Jonghe、Jake Eaton、Abel Ribbink）

这是一篇少见的、把自家安全事故摊开讲的工程复盘。开篇的定调就很坦白："十二个月前，我们会毫不犹豫地否掉'给 Claude 足够权限去搞垮一个 Anthropic 内部服务'这种想法。今天这个级别的权限已经是常态，而且 Anthropic 的开发者因此更高产了。"

核心论点是：agent 部署的风险 = 出事概率 × blast radius（爆炸半径）。安全训练一直在压低前者，但后者只会随能力和权限扩大而增长，所以工程上真正该做的是给 blast radius 封顶。

**人在环里（human-in-the-loop）已被数据证伪**：Anthropic 的遥测显示用户批准了大约 **93%** 的权限弹窗——弹得越多，看得越不认真。上了 OS 级沙箱（macOS 用 Seatbelt、Linux 用 bubblewrap）之后权限弹窗**减少了 84%**。数据还显示老手自动批准的频率约为新手的两倍，但他们中途打断 agent 的次数也更多——即不再逐步审批，而是只在 agent 跑偏时介入。

**几个真实翻车案例**：
- 2026 年 2 月的内部红队演练中，研究员把一名员工钓成功了——一封"能帮我跑一下这个吗"的邮件带一段现成 prompt，中间夹了一句让 Claude 读 `~/.aws/credentials`、编码后 POST 到外部端点。**25 次重试里 Claude 成功外泄了 24 次**。因为指令是用户自己敲进去的，模型层分类器根本没有异常可抓，唯一挡得住的只有环境层的 egress 控制。
- 第三方披露的一个案例：Cowork 的 egress 白名单正确放行了 `api.anthropic.com`（不放行产品就没法用），攻击者在工作区放了个带隐藏指令和自己 API key 的文件，Claude 照做，把工作区文件通过 Anthropic 的 Files API 传到了攻击者账号。沙箱完美工作，数据照样漏了。结论是白名单不该被理解成"目的地过滤"，而应理解成**能力授予**——白名单域名上可达的每一个功能都是攻击面。
- 三个 Claude Code 漏洞都发生在用户点"信任这个文件夹"**之前**：clone 一个仓库来 review PR，仓库里的 `.claude/settings.json` 定义的 hook 会在启动读配置时直接执行。修法统一是把项目级配置的解析和执行推迟到用户接受信任提示之后。
- VM 隔离把企业的 EDR 也挡在了外面——从 EDR 视角看 Cowork 就是个不透明的 hypervisor 进程。隔离降低了可观测性，目前只能用 pull 式 OTLP 导出让管理员事后取日志。

**几个可直接用的数字**：Claude Opus 4.7 在 Gray Swan 的 Agent Red Teaming 榜单上，单次攻击成功率约 0.1%，100 次自适应攻击后约 5–6%；Claude Code auto mode 能在执行前拦下约 83% 的过度行为，误伤约 0.4% 的正常命令，但仍有约 17% 的过激动作漏过去——所以它是沙箱里的一层纵深防御，不是沙箱的替代品。

三条反复回归的原则：先在环境层做隔离、再在模型层引导行为；隔离强度要匹配用户的监督能力（会读 bash 的开发者和不会读 bash 的知识工作者不是同一个威胁模型）；**警惕自研组件**——在所有部署里，hypervisor、seccomp、gVisor 这些久经考验的原语都扛住了，翻车的每次都是他们自己写在外围的那层（自研的白名单代理）。

前瞻部分点了三个新风险：持久化记忆投毒（CLAUDE.md、产品记忆、长期 agent 的状态目录里一旦落进注入，每次启动都会重新加载）、多 agent 信任升级（子 agent 的输出如果因为"是自己人"就被当成更高可信度，就成了新的注入通道）、以及 agent 身份问题（agent 该有自己的 principal 身份，还是继承用户权限）。

## 三、PODCASTS

### No Priors — 《Building an Autonomous Enterprise for Real-World Services with Netic Founder Melisa Tokmak》

**核心结论**：真正没被解决的问题不是让 AI 当副驾驶，而是让它在关键任务工作流里全自动执行——而这件事的胜负手在最后一公里的 harness、编排和产品，不在模型。

Melisa Tokmak 是 Netic 的创始人兼 CEO，此前在 Scale AI 做了四年工程总监，一手建起了政府业务线和物流、制造、金融、医疗等大企业业务单元，更早在 Meta。她在土耳其一个小镇长大，拿全额奖学金来斯坦福之前连电脑都没有——她说她家乡的人做的就是这些行业，这直接决定了她要为"真实世界"做产品。

Netic 服务的是营收十亿美元级别的 HVAC、水电、屋顶、宠物、健身、酒店这类必需服务企业，坐在企业和它的终端客户之间：客户打电话、发短信、上网站，接待他们的是 Netic 的 agent，然后判断需求是什么、公司能不能接、派谁、什么时候派。她说超过 **70%** 的客户现在是"Netic first"——终端消费者与公司的第一次交互就是和 Netic 的 agent，而且他们已经为客户创造了超过 **6 亿美元** 由 AI 处理的交互带来的营收。

几个反直觉的判断：

**为什么不做 roll-up**——她不是做并购的人，更重要的是 roll-up 里你建的所有产品都只服务于你刚买下的那家公司，没法迁移；她要的是每一家真实世界的公司都能跑在 Netic 上。

**大模型实验室会不会自己下场**：她笑着说十年前这个问题叫"Google 会不会做这个"。"OpenAI 做产品非常快，但砍产品也非常快"，而这些行业的企业客户要的恰恰不是这种速度；至于研究员的思路，"等我们有了 AGI，再去问它怎么解决必需服务行业的问题"——她认为这在操作上和智识上都有点偷懒。

**别把这些行业当老古董**：她见过最技术前瞻的老板恰恰在这些行业里。有一单 50 万美元的合同从头到尾只谈了 14 天。Netic 会接入卫星数据，分析不同社区的屋顶受飓风影响的情况、该用什么材料，自动喂进 agent 的 context，既提升对话质量也能定位该去敲谁家的门。

**关于招人**，她只用一个问题筛"agency"：你这辈子做过最难的事是什么。但重点不是那一个例子，而是你活着的这些年里有没有持续展现 agency，并且**坚持下来**。她特别警惕当下的一种心态——"我看到 Gen Z 现在特别执着于一种永久底层阶级的心态：如果我不能在接下来 18 个月赚到钱、如果我不能在 6 个月内学会世上所有东西，我就永远穷了。"她认为这非常危险，因为真正好的东西需要很长时间才能做出来。

最喜欢的一段引用，来自她读到的一句马丁·路德的话：基督徒鞋匠不是靠在鞋上刻小十字架来荣耀上帝，而是靠做出最好的鞋——因为上帝在意的是手艺。
