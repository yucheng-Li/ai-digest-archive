### Anthropic Engineering

**How we contain Claude across products**

十二个月前，Anthropic 还会毫不犹豫地否决"给 Claude 足以搞垮一个内部服务的权限"这种想法；今天这种权限级别已经是日常，工程师的产出也因此提高了。文章把 agent 部署的风险拆成两部分：失败概率，以及一次失败能造成多大破坏。前者靠模型训练和防护手段在持续下降，后者——理论上的"爆炸半径"——只会随能力和权限扩张而变大。

最刺眼的一个数字来自人工审批这条路线：遥测显示用户批准了大约 93% 的权限弹窗。"看到的审批越多，每一个就看得越不认真"，长期下来监督质量急剧退化。Claude Code 的 auto mode 就是为了缓解这种审批疲劳而做的，但任何概率性防御都有非零漏判率。

所以文章的重点落在第二条路线：容器化隔离。与其监督 agent 做了什么，不如限制它能做什么——用沙箱、虚拟机和出口流量控制来强制访问边界。claude.ai、Claude Code、Claude Cowork 三个 agent 产品面向不同人群，隔离架构各不相同，文章逐一讲了哪些设计扛住了、哪些崩了。另一个值得注意的信息：Claude Mythos Preview 就是一个因为爆炸半径被判定过高、在 2026 年 4 月被决定不发布的模型。

https://www.anthropic.com/engineering/how-we-contain-claude

**An update on recent Claude Code quality reports**

针对"Claude 变笨了"的持续反馈，Anthropic 给出了复盘：三处独立改动分别影响了 Claude Code、Claude Agent SDK 和 Claude Cowork，API 未受影响，三个问题均已在 4 月 20 日（v2.1.116）修复。

具体是：3 月 4 日把 Claude Code 默认 reasoning effort 从 high 降到 medium（为了解决 high 模式下延迟长到界面像卡死的问题），这是个错误的取舍，4 月 7 日回滚，影响 Sonnet 4.6 和 Opus 4.6；3 月 26 日上线了"闲置超一小时清理旧 thinking"的优化，但 bug 导致它在整个会话里每轮都执行，Claude 因此显得健忘且重复，4 月 10 日修复；4 月 16 日加了一条降低啰嗦程度的 system prompt，叠加其他 prompt 改动后损害了编码质量，4 月 20 日回滚，影响 Sonnet 4.6、Opus 4.6 和 Opus 4.7。

三处改动各自作用于不同流量切片、不同时间线，叠加起来就呈现为"大范围且不一致的退化"。他们承认早期难以把这些反馈和正常波动区分开，内部使用和 evals 一开始都没复现出问题。作为补偿，4 月 23 日起为所有订阅用户重置了用量额度。

https://www.anthropic.com/engineering/april-23-postmortem

**Scaling Managed Agents: Decoupling the brain from the hands**

核心论点：harness 本质上是在编码"Claude 自己做不到什么"的假设，而这些假设会随着模型变强而过期。举的例子很具体——Sonnet 4.5 会在感知到上下文快满时草草收尾（所谓 "context anxiety"），他们为此在 harness 里加了 context reset；换到 Opus 4.5 上这个行为消失了，这段逻辑就成了死重。

于是他们做了 Managed Agents：Claude Platform 上托管长周期 agent 的服务，接口设计刻意做得比任何具体实现活得更久。类比是操作系统当年把硬件虚拟化成 process、file 这类抽象——read() 不关心底下是 1970 年代的磁盘还是现代 SSD。Managed Agents 同样把 agent 拆成三层虚拟化组件：session（记录一切的 append-only 日志）、harness（调用 Claude 并把工具调用路由到基础设施的循环）、sandbox（跑代码改文件的执行环境），三者可以各自替换互不影响。

踩过的坑也写得很实在：最初把三者塞进同一个容器，结果"养了只宠物"——容器挂了 session 就没了，容器卡住就得人工救活，而唯一的观测窗口只有 WebSocket 事件流，根本分不清故障出在 harness 还是丢包。

https://www.anthropic.com/engineering/managed-agents

### Claude Blog

**Claude Code now supports artifacts**（2026 年 6 月 18 日）

Claude Code 现在可以把工作进展直接产出为 artifact——一个会随会话自动更新的、可分享的可视化网页：PR 走查、系统说明、dashboard、发版 checklist 都能这么做。

关键在于它是基于会话全部上下文构建的：代码库、连接器、对话本身。一个故障排查页面可以同时包含失败的测试和背后的函数（来自代码）、监控工具里的错误率尖峰（来自连接器）、以及刚跑完那轮会话的根因推理，不需要自己接数据源或起服务。页面是活的——Claude Code 更新 artifact 时，已经打开的页面会原地刷新，队友立刻看到；每次发布都是同一链接下的新版本，有版本历史可回滚，还有 gallery 统一管理。

内部测试中最高频的用法是 debug：工程师在站会前启动故障调查，Claude Code 翻完日志发布一个 artifact——时间线、可疑提交、错误率图表；等站会开始，它已经随调查进展重新发布了两次。团队成员不需要再听人"讲一遍 agent 发现了什么"，因为大家看的是同一个视图。

权限上，artifact 默认仅作者可见，分享后也只有组织内通过认证的成员能看，无法公开；管理员可通过组织级开关、基于角色的范围控制、留存策略和合规 API 统一管理。

### AI & I by Every — How a Professional Writer Writes With AI

**一句话结论**：AI 写作的胜负手不在模型，而在你能提供多少模型拿不到的东西——知识截止日之后的真实世界经验、独家数据和个人经历。

Katie Parrott 是 Every 的专职作者。两年多前她刚被一家加密公司裁掉，正处在心理健康的低谷，请不起每小时 150 美元的职业教练，于是花 20 美元订了 ChatGPT 当教练用——而那时她还是个 AI 怀疑论者。这条线一路走到今天：她的"职业教练"现在是 Codex 里的一个项目，装着关于她本人和岗位的档案、公司品牌定位、OKR、绩效数据，甚至还有一个她称为"validation folder"的文件夹，专门收集别人夸她作品的好话——目的是让模型理解读者对她哪部分内容反应最好。这个教练现在替她做优先级排序、项目管理，还自动维护一块看板："我从来不是那种能维护看板的人，现在我根本不用碰它。"

她对 AI 写作最锋利的判断是"最后一公里问题"：模型的知识永远滞后几个月，人类的活儿就是补上这一段——真实世界的经验、独家研究、个人经历。"很多人用 AI 写东西，就是丢一句'写篇关于 style guide 的博客'，不给任何输入。可模型已经知道的东西是同质化信息，没用也没意思。"

她新做的 Compound Writing 插件是从 Kieran Klassen 的 Compound Engineering 直接 fork 来的，核心理念是同一个反馈只该给一次，编码进系统后永久生效。有意思的是里面的审阅者设计：她把 Vonnegut 的八条故事结构原则（"尽可能贴近结尾开场""每句话都得挣到自己的位置"）做成了一个 skill，把 Hitchcock 的悬念原理（桌下的炸弹爆炸只是一秒惊吓，先告诉观众炸弹五分钟后爆炸才是五分钟悬念）做成另一个，还有 Sorkin、Sedaris。写完随时可以"召唤"其中一个视角来审自己的稿子。她把这套东西形容成健身房，不是省力工具。

她还讲了 AI 作为"支撑性技术"而非"生产性技术"的一面：她有双相情感障碍，拖了三年没约的家庭医生，最后是让 Codex 去找附近收她保险、还接新病人的医生，直接约上了。不过 AI 也会给她挖坑——她给自己做的 Tastemaker 应用加了个 MCP，Claude 爽快地写完，转头让 Codex 审，审出五个安全漏洞。

她在 11 月 Every 大会上要讲的论点是"教育和可及性从未如此重要"：她住在俄亥俄州哥伦布市，没在纽约、SF、奥斯汀待过，很清楚自己能玩得起这些工具靠的是一定的经济余裕和空闲时间。"AI 有巨大的乘数效应和复利效应，但风险在于这份价值只会向那一小撮碰巧入场早的人复利。"
